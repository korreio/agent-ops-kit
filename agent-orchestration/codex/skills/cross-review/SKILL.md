---
name: cross-review
description: Coordinate a review of code or reviewed prose using roster roles, independent claim verification, and the installed cross-family launchers.
---

Size the package from its repository contract and standing order 3. Read
`roster.md` in the supplied toolkit directory; names and efforts belong there.
The coordinator owns Git, test leases, the candidate, fixes and the review record.
For a small change use one fresh reviewer; ordinary adds an other-family reviewer
when reachable; big uses reviewer-deep, reviewer-wide and an other-family reviewer.
Standing order 3 sizes the review of a plan or other prose. In plan mode, a fresh
reader runs orchestration reference §8's readiness check, and the coordinator budgets
the verification of every gap before anyone acts on it.

Materialize the patch or name whole files in a scratch brief. Include the contract,
context paths, hazards, acceptance, allowed reads and budget. Workers never run git diff,
mutate Git, run unassigned wrappers or edit singletons. Keep secrets out of briefs.
Native writer agents pin roster instructions and effort but inherit parent permissions.
Read-only roles run through `codex-review --role ROLE`; their native agent instructions
alone cannot enforce read-only access. The launcher selects its independent read-only profile.
Use `claude-review` for the other family, pinned to its roster reviewer row;
`claude-write` handles an authorized writer lane. Use installed launchers rather than
hand-built commands. Claude reviewers use reading tools only; supply materialized command and
resolved link-target evidence in their brief. Intentional editing uses the separate writer lane.

Launch independent reviewers on the same candidate and continue useful work while they run.
Each claim must name severity, file:line, what a user does and how often (for a plan, the step
that goes wrong), failure and smallest fix.
Collect CLEAN, FINDING or BLOCKED with checked paths and limitations. A failed tool is not a
verdict: use a fresh reviewer that did not write the candidate and report the missing coverage.

Before fixes, a verifier who was none of the reviewers tries to refute every claim against code;
record CONFIRMED, REFUTED or DOWNGRADED and check the proposed fix's owner. Fix confirmed defects,
run assigned real checks, then review only what changed. Never let a reviewer fix its own claim.
If the same piece fails twice, start from before the patches in a different direction, designed
or written by the other family. There is no automatic review loop or quota-draining Stop hook.

Keep one line per review where the repository keeps evidence: roles and families, claims raised,
confirmed, refuted or downgraded, checks run, unproved work and verdict. Report by four fifths
of the brief budget or before ending even unfinished: at most ten summary lines then evidence.
